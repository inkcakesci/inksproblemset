## 问题

接口可能收到空字符串、缺失边界和不同格式的时间，后端应该如何兼容并避免错误筛选？

## 答案

时间参数应在 API 边界统一规范化为明确时区的类型，例如 `ZonedDateTime` 或 `Instant`，不能让各 DAO 自行解析字符串。空字符串先归一为 null；格式非法应返回明确参数错误，不能静默当作“无筛选”。

项目查询中只有开始和结束都有效时才应用完整时间范围，这可以兼容旧前端传空值。但长期契约还应明确单边时间的语义：支持 `>= start`、`< end`，或明确要求成对提供，避免调用方猜测。

实践要点：

- API 指定 ISO-8601 和时区；数据库统一存 UTC，展示时再转换用户时区。
- 推荐半开区间 `[start, end)`，避免毫秒精度和一天结束时间产生遗漏。
- 校验 start 不晚于 end，并限制最大查询跨度，保护大表。
- 不要用服务器默认时区解释商户传入的无时区字符串。
- 列表、汇总和导出复用同一转换结果，并测试夏令时边界。

兼容旧格式应该是可观测的过渡策略，记录使用量并逐步淘汰，而不是永久接受任意时间字符串。
