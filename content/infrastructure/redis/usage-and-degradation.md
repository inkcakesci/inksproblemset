## 问题

Redis 用于验证码、缓存、状态控制和队列基础设施时，如何设计 TTL、失效策略和故障降级？

## 答案

Redis 的策略要按用途区分：验证码使用短 TTL、次数限制和一次性消费；缓存根据数据新鲜度设置 TTL，并加随机抖动防止集中失效；锁或状态控制要有 owner token、租约和安全释放；如果承载队列，则要评估持久化、确认和重放语义，不能把普通缓存配置直接当可靠消息系统使用。

故障降级也不能一刀切：普通缓存可以回源数据库并限流，验证码和支付锁等安全关键场景应 fail closed，不能因为 Redis 挂了就跳过校验或并发控制。

### 展开回答

- Key 按环境、业务、租户和版本命名，避免碰撞和批量误删。
- 热点缓存可用逻辑过期、single-flight 或互斥重建，防止缓存击穿。
- 删除与数据库更新存在竞态时，使用明确的失效或事件驱动更新策略。
- 分布式锁不是账务唯一性保障，支付仍需数据库唯一约束和状态机兜底。
- 监控命中率、延迟、内存、淘汰、连接数、复制延迟和持久化失败。

### 项目实践

为每种 Key 建立登记表，写清 owner、TTL、数据敏感度和故障行为。Redis 不可用时，Profile 缓存可降级回源；验证码暂停验证；支付 Worker 则依赖持久化数据库状态恢复，而不是悄悄跳过锁继续执行。
