## 问题

邮箱验证码为什么需要 Redis、TTL、Hash 和一次性消费？如何防止暴力破解和重复使用？

## 答案

验证码是短生命周期、强时效的临时凭证，很适合放在 Redis。服务端不应明文保存验证码，而应保存带业务上下文的 Hash，并设置较短 TTL。验证成功时要用原子操作完成“校验并删除或标记已消费”，避免并发请求重复使用。

防暴力破解还需要发送频率限制、按账号与 IP 限制验证次数、失败锁定、重发冷却和统一错误信息，不能只依赖六位数字本身的复杂度。

### 展开回答

- Key 应包含用途、用户或邮箱、challengeId，避免注册验证码被用于修改密码。
- Hash 输入应绑定验证码和 challenge 上下文，并使用服务端秘密，防止 Redis 数据泄露后被离线枚举。
- 验证成功、次数耗尽和超时后都应立即失效。
- 重发时使旧 challenge 失效，避免多个验证码同时有效。
- 对账号、邮箱、IP、设备等维度分别限流，并记录异常尝试供风控使用。
- 响应不要暴露“邮箱是否存在”，防止账号枚举。

### 项目实践

关键验证流程在 Redis 故障时应 fail closed，不能因为缓存不可用就跳过验证。验证码验证与最终敏感操作之间还应绑定一次性的 verification ticket，避免“验证码通过”和“业务提交”之间被替换参数。
