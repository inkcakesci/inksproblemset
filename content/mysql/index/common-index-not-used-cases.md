## 问题

MySQL 中有哪些常见的索引无法被有效利用的场景？应该如何判断？

## 答案

常见场景包括：

1. **联合索引不满足最左前缀**：索引为 `(name, age, city)` 时，只按 `age` 或 `city` 查询通常无法利用该索引快速定位。
2. **对索引列使用函数或计算**：如 `DATE(create_time) = ...`、`age + 1 = 26`，可能无法直接利用原索引的有序性。可以改写成对原列的范围或等值条件。
3. **`LIKE` 以前置 `%` 开头**：`LIKE 'Alice%'` 通常可以利用索引前缀，`LIKE '%Alice'` 通常不能用 B+ 树快速定位。
4. **隐式类型转换**：字符串列与数字比较等情况可能使索引无法被有效使用，应保持参数类型与列类型一致。
5. **联合索引遇到范围条件**：索引为 `(a, b, c)`，条件为 `a = 1 AND b > 10 AND c = 20` 时，`b` 之后的 `c` 通常不能继续缩小 B+ 树的扫描区间，但在部分版本和场景中仍可能参与索引条件下推。
6. **`OR` 一侧缺少可用索引**：优化器可能认为全表扫描成本更低。
7. **选择性太低或返回比例太高**：即使存在索引，大量回表也可能比全表扫描更贵，优化器会主动放弃索引。

优化建议不能只靠规则猜测，应结合数据分布和 `EXPLAIN`、`EXPLAIN ANALYZE` 查看访问类型、候选索引、实际使用索引、估算行数及真实执行情况。

例如，不要写：

```sql
WHERE DATE(create_time) = '2026-07-29'
```

可以改为：

```sql
WHERE create_time >= '2026-07-29 00:00:00'
  AND create_time <  '2026-07-30 00:00:00'
```
